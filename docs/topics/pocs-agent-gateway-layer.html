After the standard, the operations layer

The MCP SDK now outpaces every tracked AI package on npm, and once a standard stops being contested an operations layer grows on top of it. What is hot is not a model but the gateway sitting between agents and their tools — and per-agent spend limits are a cell this project leaves empty.

Ten minutes: run LiteLLM in proxy mode from its README and stop at the point where cost tracking switches on — that single moment is the whole demonstration. Optional: write one line on what would become visible if this project's own agent tool calls ran behind a gateway. Sources to confirm, because all of the figures below are vendor or secondary: the MCP npm SDK download count, and TrueFoundry's published latency and throughput numbers.

Why

A standard winning is not the end of a story, it is the start of a different one. While the protocol was contested, the interesting work was the protocol. Once it stopped being contested — the MCP SDK is now reported at roughly 195.9 million monthly npm downloads, ahead of every other tracked AI package — the interesting work moved one layer up, to whatever sits between an agent and the tools it calls. That layer is where identity, spend and access controls live, and it did not exist a year ago because nothing was standard enough to put a gateway in front of.

This is not a blockchain item, and that is the point. The report's rotation reached the general build stack, and the general stack turns out to be needed sooner than the queue implies. This catalogue already has mcp-stateless-server for building a server on the spec, agent for an autonomous payment agent, and senpi-harness for running one — three cards about producing agents, none about governing them.

The empty cell is specific and close to home. This report is itself produced by an agent, with real tool calls and a real bill, and there is currently no per-agent identity, no spend ceiling and no record of which tool consumed what. Those are exactly the three things an agent gateway provides. The question worth asking is not which vendor to pick — it is what the ledger would say if one were switched on for a week.

How it works

What is in the layer

Piece What it does Where it fits
LiteLLM Rust-core gateway putting 100+ LLM APIs behind one interface, with cost tracking and load balancing Makes model swaps a config change rather than a code change
TrueFoundry Split into an MCP gateway governing every tool connection and an agent gateway carrying per-agent identity and spend limits The governance half; published at roughly 3-4ms added latency and 350+ RPS on 1 vCPU
katanemo/plano AI-native proxy and data plane with smart LLM routing The routing half, for agent apps
vLLM High-throughput serving on PagedAttention The default once serving moves in-house
Context compression Separating into its own infrastructure layer Emerging, because agents have hit real token-cost ceilings

The measurement, and it is one week long

Put this project's agent tool calls behind a gateway for a week and read three numbers off the ledger: cost per report section, which tool dominates the bill, and how much of the spend is context rather than output. None of the three is currently knowable, and all three change what is worth optimizing. The last one is the reason context compression is becoming its own layer, and a measured ratio would say whether that matters here or is somebody else's problem.

The unglamorous reason this belongs on the list

Every card in this catalogue about agents is about making one work. A gateway is about what happens when one misbehaves — a loop that calls a paid tool a thousand times, a credential reachable by an agent that should not reach it. Those are operational failures rather than interesting ones, which is exactly why the layer exists and exactly why it gets added after the incident rather than before.

표준 다음에 오는 운영 계층

MCP SDK가 npm에서 추적되는 모든 AI 패키지를 앞질렀고, 표준 경쟁이 끝나면 그 위에 운영 계층이 자랍니다. 지금 뜨거운 것은 모델이 아니라 에이전트와 툴 사이에 앉는 게이트웨이이고 — 에이전트별 비용 한도는 이 프로젝트가 비워 둔 칸입니다.

10분: LiteLLM README의 프록시 모드를 한 줄로 띄우고 비용 추적이 켜지는 지점에서 멈춥니다 — 그 순간 하나가 시연의 전부입니다. 선택: 이 프로젝트의 에이전트 툴 호출을 게이트웨이 뒤로 옮기면 무엇이 보이게 되는지 한 줄로 적기. 확인이 필요한 출처 — 아래 수치는 전부 벤더 또는 2차 자료입니다: MCP npm SDK 다운로드 수, TrueFoundry가 공개한 지연·처리량 수치.

왜

표준이 이겼다는 것은 이야기의 끝이 아니라 다른 이야기의 시작입니다. 프로토콜이 다퉈지는 동안에는 흥미로운 일이 프로토콜이었습니다. 다퉈지지 않게 된 순간 — MCP SDK가 월 약 1억 9,590만 npm 다운로드로 추적되는 다른 모든 AI 패키지를 앞섰다고 보고됩니다 — 흥미로운 일이 한 층 위로, 에이전트와 그것이 호출하는 툴 사이로 옮겨갔습니다. 신원·비용·접근 통제가 사는 층이고, 1년 전에는 존재하지 않았습니다. 게이트웨이를 앞에 세울 만큼 표준화된 것이 없었으니까요.

블록체인 항목이 아니라는 점이 오히려 요점입니다. 리포트의 순환이 일반 빌드 스택에 닿았는데, 그 일반 스택이 큐가 암시하는 것보다 빨리 필요합니다. 이 카탈로그에는 명세 위에 서버를 만드는 mcp-stateless-server, 자율 결제 에이전트 agent, 그것을 돌리는 senpi-harness 가 있습니다 — 에이전트를 만드는 카드 셋, 에이전트를 통치하는 카드 영.

비어 있는 칸은 구체적이고 가깝습니다. 이 리포트 자체가 에이전트가 만들고, 실제 툴 호출과 실제 청구서가 있는데, 지금 에이전트별 신원도, 지출 상한도, 어떤 툴이 얼마를 썼는지의 기록도 없습니다. 에이전트 게이트웨이가 주는 것이 정확히 그 셋입니다. 물어야 할 질문은 어느 벤더를 고를까가 아니라 — 일주일 켜 두면 그 장부가 무엇을 말할까 입니다.

동작 방식

이 층에 무엇이 있나

조각 하는 일 어디에 맞는가
LiteLLM Rust 코어 게이트웨이. 100개 이상 LLM API를 단일 인터페이스로 묶고 비용 추적·로드밸런싱 모델 교체를 코드 변경이 아니라 설정 변경으로 만듦
TrueFoundry MCP 게이트웨이(모든 툴 연결 통제) + Agent 게이트웨이(에이전트별 신원·비용 한도) 통치 쪽 절반. 공개 수치 1 vCPU에서 약 3~4ms 추가 지연, 350+ RPS
katanemo/plano 에이전트 앱용 AI 네이티브 프록시·데이터플레인, 스마트 LLM 라우팅 라우팅 쪽 절반
vLLM PagedAttention 기반 고처리량 서빙 자체 호스팅으로 내려갈 때의 기본값
컨텍스트 압축 별도 인프라 층으로 분리되는 중 에이전트가 실제 토큰 비용 한계에 닿았기 때문에 부상

측정, 그리고 기간은 일주일

이 프로젝트의 에이전트 툴 호출을 일주일간 게이트웨이 뒤로 넣고 장부에서 숫자 셋을 읽습니다 — 리포트 꼭지당 비용, 청구서를 지배하는 툴, 지출 중 출력이 아니라 컨텍스트가 차지하는 비중. 지금은 셋 다 알 수 없고, 셋 다 무엇을 최적화할지를 바꿉니다. 마지막 것이 컨텍스트 압축이 자기 층이 되어 가는 이유이고, 비율을 재 보면 그게 여기서 문제인지 남의 문제인지가 정해집니다.

목록에 있어야 하는 멋없는 이유

이 카탈로그의 에이전트 카드들은 전부 하나를 작동시키는 이야기입니다. 게이트웨이는 하나가 잘못 굴러갈 때의 이야기입니다 — 유료 툴을 천 번 호출하는 루프, 닿으면 안 될 자격증명에 닿는 에이전트. 흥미로운 실패가 아니라 운영상의 실패이고, 그래서 이 층이 존재하며, 그래서 사고 전이 아니라 사고 후에 추가됩니다.
