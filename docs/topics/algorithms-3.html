Persistent Data Structures and Structural Sharing TODO

Algorithms · Day 3 / 100 · A. Advanced Algorithms & Data Structures (Day 1-19)

Concept

A persistent data structure is one where an update never destroys the existing version — it creates a new version while the old one stays readable. The key technique is structural sharing: only the nodes along the changed path get copied, while the rest of the subtree keeps pointing at the previous version unchanged. In a balanced tree or trie-based structure, the path length from the root to the change point is O(log n), so both the time and the extra memory for a single update stay at O(log n). Partial persistence (old versions are read-only) is distinguished from full persistence (old versions can be updated again too), and functional languages' immutable lists or a HAMT (hash array mapped trie) are the classic examples. Immutability means a snapshot of a prior version comes essentially for free, and readers can traverse safely without a lock.

In systems that need multiple versions alive at once — rollback, snapshot isolation, undo, optimistic concurrency — copying everything on every update costs O(n).

Code & Formula

# 영속 연결 리스트 — 구조 공유로 갱신마다 새 버전을, 이전 버전은 그대로.
# cons(x, node) 는 새 헤드 노드 하나만 만들고 나머지 체인은 공유한다 — O(1) 갱신.

class Node:
    __slots__ = ("value", "next")
    def __init__(self, value, next=None):
        self.value = value
        self.next = next

def cons(value, node):          # 새 버전 하나 생성 (기존 node 는 손대지 않음)
    return Node(value, node)

def to_list(node):
    out = []
    while node:
        out.append(node.value)
        node = node.next
    return out

v0 = None
v1 = cons(1, v0)                # v1: [1]
v2 = cons(2, v1)                # v2: [2, 1] — v1 의 노드를 그대로 공유
v3 = cons(3, v1)                # v3: [3, 1] — v2 와 무관하게 v1 에서 또 분기

print("v1 =", to_list(v1))      # [1]
print("v2 =", to_list(v2))      # [2, 1]
print("v3 =", to_list(v3))      # [3, 1]  ← v1 을 공유하지만 v2 와 독립
print("v2 tail is v1 node:", v2.next is v1)  # True — 복사 없이 포인터 공유

Exercise

Implement an immutable list or a simple HAMT yourself, insert 10,000 entries while keeping every intermediate version, and compare the memory and time cost against a full-copy-every-time approach.

Practical Connection

Ethereum's state trie is exactly a persistent data structure — each block writes only the nodes along the changed path and shares the rest with the previous root, so a single root hash can trace the entire state as of a specific block.

Algorithms · Day 3 / 100 · A. 고급 알고리즘·자료구조 (Day 1–19)

불변 상태의 O(log n) 갱신

개념

영속(persistent) 자료구조는 갱신 연산이 기존 버전을 파괴하지 않고 새 버전을 만들며, 이전 버전도 계속 조회 가능한 자료구조다. 핵심 기법은 구조 공유로, 변경된 경로 위의 노드만 새로 복사하고 나머지 서브트리는 이전 버전과 포인터를 그대로 공유한다. 균형 트리나 트라이 기반 구조에서는 루트부터 변경 지점까지의 경로 길이가 O(log n)이므로 갱신 한 번의 시간과 추가 메모리도 O(log n)에 머문다. 과거 버전을 읽기만 가능한 부분 영속성과 과거 버전에서 다시 갱신까지 가능한 완전 영속성을 구분하며, 함수형 언어의 불변 리스트나 HAMT(hash array mapped trie)가 대표 사례다. 불변성 덕분에 이전 버전 스냅샷이 사실상 공짜로 생기고, 읽는 쪽은 락 없이 안전하게 순회할 수 있다.

롤백, 스냅샷 격리, undo, 낙관적 동시성처럼 여러 버전을 동시에 살아 있게 해야 하는 시스템에서 매 갱신마다 전체 복사를 하면 O(n) 비용이 나기 때문이다.
