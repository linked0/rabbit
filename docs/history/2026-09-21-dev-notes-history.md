Cost, stated plainly: Google's SDK becomes the first third-party script this site has ever loaded, which only the fallback rule makes acceptable. A visitor fetches none of it — the SDK loads only after the "Edit" link in the rail foot is tapped, or on a device that signed in before.
- **Change:** Firestore (native, asia-northeast3) and a Firebase web app in **doubletree-498007**; Authentication initialised, Google sign-in enabled (the OAuth client is console-only, so jay clicked that one toggle), authorized domains set to `alice.jaylabs.xyz` and `localhost`. `infra/firestore.rules`, deployed and live: only jay's verified Google email reads or writes, the status document shape is validated, health documents hold ciphertext only, everything else denied. `docs/topics/_status.js` — sign-in, per-item status buttons, and an overlay that repaints the rail dots for pending changes. The loader is appended to `docs/topics/_progress.js`, which all 776 rail pages already load, so no generated page was touched.
- **Result:** a status can be set from the phone without typing a key, without a credential in storage, and without a server. The number beside an item still comes from the built page, so a pending change shows as a dotted dot and settles at the next rebuild — flagged rather than hidden. **Still open:** the drain workflow that folds the queue into the repo and empties it, and moving the health ciphertext out of the public repo into the same database.

### The overlay reproduces a rebuild in the page, so no rebuild is needed

- **Cause:** jay pushed back on the drain: "we don't need to change the files in the repo because we use Firestore. I don't see why we need to worry about GitHub Actions." He was right, and I had let an optional tidy-up grow into a requirement.
- **Reasoning:** the drain was never needed for the feature. It existed to keep the built pages honest and to settle the numbers, and neither has to happen quickly or by a machine. Recolouring alone is not enough, though: a number here is derived from status rank, so marking one item done changes the number of every item after it, and a green dot beside a planned number is a page that contradicts itself. So the overlay now reproduces what a rebuild does — apply the queue, re-rank each section with the same stable sort by rank, renumber from the section base, repaint the dots, reorder the rail and the card list, and recompute the jump pills, the article counts and the rail badge. Nodes are moved rather than rebuilt so the current-page highlight and the page's own handlers survive. Queued items keep a dotted ring: shown as live, marked as not yet written back. Verified before deploy by running the same ranking over the real `_nav.js` with no overrides — all 923 numbers came out identical to the built ones, so the client-side rule matches `reorder-by-status.py` and `english-notes.py` rather than approximating them.
- **Change:** `docs/topics/_status.js` rewritten. `BASE` and `RANK` are mirrored from `notes_numbering.py` and `reorder-by-status.py` and must move with them. GitHub Actions, workload identity and the drain are dropped from the design; the `alice-status-drain` service account is left unused and can be deleted.
- **Result:** a status set from the phone shows correctly and immediately — dot, rank order, number and counts — with no rebuild, no server and no credential stored anywhere. What stays stale is only what a visitor sees, which is the right split: the public gets the published snapshot, jay gets his live state. The workflow from earlier today (`set-status.yml`) still exists and still works from the Actions tab; it needs no Google credential because it never reads Firestore.

### Health ciphertext moves to Firestore, and the overlay stops reshuffling a correct page

- **Cause:** jay: "if we put the health items into Firestore, we don't need to encrypt them, because we'll use Google sign-in." Then, after the overlay shipped: "when you go to the Eng list from an Eng card there's some blinking, can you check."
- **Reasoning (encryption):** sign-in and encryption answer different questions, so I kept both and said why with evidence rather than principle. Firestore security rules govern browser clients only — anything holding a service account credential reads straight through them. This project has three such identities, including the default Compute Engine account, which carries `roles/editor` project-wide and is what the devnet VM runs as. That VM has a public RPC, has been stalling, and its own runbook records an API key visible in the process list. Without client-side encryption, one compromised box reads the health text. So: sign-in decides who may *fetch* the bytes, the password decides who may *read* them. The honest cost is that there is no reset — lose the passphrase and the text is gone. Nothing was re-encrypted; the same bytes moved, so no passphrase was needed to migrate.
- **Reasoning (blinking):** the overlay called its repaint on every sign-in, and the repaint re-appended every rail item and every card unconditionally. Re-appending a node that is already in place still detaches and reinserts it, so a list of nine hundred items reflowed in full and flashed — while changing nothing, since with an empty queue the built page is already correct. Three fixes, cheapest first: return immediately when nothing is queued and nothing was ever repainted; compare the computed order against the DOM order and move nodes only when they differ; and write a colour, title, ring or number only when the value is not already what it should be.
- **Change:** `health/bundle` document written with the existing blob; `docs/topics/_health.js` cut from 22,325 bytes to 124, labels only; `scripts/health-cards.py` page code fetches the bundle after sign-in and decrypts as before; `scripts/health-encrypt.mjs` writes ciphertext to Firestore and labels to the repo; README and docstring rewritten. `docs/topics/_status.js` made a no-op when nothing changed.
- **Result:** no ciphertext anywhere in `docs/`. Reading a Health item now needs sign-in **and** the password. The old ciphertext stays in git history, which jay accepted. The Eng list should no longer flash, because with an empty queue the overlay touches nothing at all.

### The rail badge cached its totals, so the overall count ignored queued changes

- **Cause:** jay sent a screenshot of the live rail: the Eng pill read 3 of 398 while the overall badge still read 71 of 923. The section counts add to 73, so the badge was stale rather than merely rounded.
- **Reasoning:** `_progress.js` summed `nav.jump` once at load into two closure variables and `paint()` reused them. The badge is also a button — clicking it toggles the all-sections rail and repaints — so any repaint after the overlay ran wrote the load-time numbers straight back over the new ones. The "All ·" prefix in the screenshot was the giveaway: that shape is only produced by `paint()`, so a repaint had happened after the overlay's write. The overlay was also at fault for writing the badge's text at all, since that made it own a shape belonging to another file, and it dropped the "All ·" label in the process.
- **Change:** `_progress.js` recomputes the totals on every read instead of caching them, the milestone check reads the same live figure, and `paint()` is exposed as `window.__RAIL_REPAINT__`. `_status.js` now updates `nav.jump` — the data the badge reads — and asks the badge to repaint itself, falling back to writing the text in the correct shape only if the hook is missing.
- **Result:** verified by simulation against the real nav data — marking two Eng items done gives an Eng pill of 3 of 398 and a badge of 73 of 923, which agree. The lesson worth keeping: a value cached at load will be written back over anything that changes it later, so the fix belongs in the data, not in the rendered text.

### The badge fix depended on two independently cached files, so it did not reach the phone

- **Cause:** after the previous fix, jay still saw it: "after the English count changes, there's no change in the total count."
- **Reasoning:** the code was right and I proved it rather than assuming — running `_progress.js` against the real nav data in a stub page, the repaint hook is exposed and the badge follows `nav.jump` from 71 to 73. The flaw was in how the fix was *delivered*. `_progress.js` and `_status.js` are separate files on a ten-minute cache, so a browser can hold a new copy of one and an old copy of the other. The previous fix only worked when **both** were fresh: it updated the shared data and asked the badge to repaint itself. A browser still running yesterday's `_progress.js` repaints from totals it captured at load and writes the old number straight back, and nothing in the new file can stop it. The earlier screenshot said as much — "All · 8% · 71/923" is the repaint's text shape carrying the pre-overlay number, so a repaint had run last.
- **Reasoning (the general point):** a fix that needs two independently cached files to be in step is not one fix, it is a race. The overlay has to be correct on its own.
- **Change:** `docs/topics/_status.js` — a `setBadge()` that asks the badge to repaint from the shared data *and then* writes the value itself regardless, plus a `rail-all-change` listener that re-asserts it after any later repaint. `_progress.js` registers its listener at parse time and the overlay is deferred, so the overlay's listener runs second and has the last word. With both files fresh the second write is a no-op.
- **Result:** verified two ways — the hook path still carries 71 to 73, and a simulated stale repaint writing 71 is overwritten back to 73 by the re-assert. jay still needs one cache-busted load to pick up the new overlay; after that, no combination of cached files shows a wrong total.

### A pass count: items finished twice, and three times

- **Cause:** jay: "I want to add a property for items that are done twice, and three times. How can we do that?"
- **Reasoning:** store the dates, not the count. A count and a list of dates can disagree; a list alone cannot, and it also keeps the gap between passes, which is the number that actually says whether a second reading was a week later or three months later. The existing `done` field stays as the most recent stamp so every reader of it is untouched, and `dones` is added beside it; an item with only `done` counts as one pass. A repeat only counts on a **different done-day**, reusing the 06:00 KST boundary — a second tap in one sitting moves the existing entry rather than adding one, so a stray press cannot inflate the history. Shown as a numeral beside the dot rather than a new colour, because colour already means status and a twice-done IMPORTANT item would collide. One filter button, not two: the rail already carries seven.
- **A bug caught before shipping, and one after.** I first put the count in the dot's `title` — but every tier filter compares that string exactly, so a repeated item would have silently dropped out of New, Today and Revisit. The count moved to `data-times` only, and the same latent fault was fixed in the overlay, which had been appending "(queued)" to the title since this morning. Then the count reached the data but not the page: `reorder-by-status.py` calls `roll-done-states.py` **only when something expires from NEW**, so a plain status change never re-synced the dots, counts, badge or card chips. The data said DONE while the page still said PLANNED. `set-status.py` now runs the sync last, unconditionally.
- **Change:** `set-status.py` (`dones`, the same-day rule, the sync); `english-notes.py` carries `dones` from the Eng markdown; `roll-done-states.py` writes `data-times`; `rtd-shell.mjs` renders it for new pages; the numeral CSS added to all 923 detail pages and the `Repeated` filter to the 775 that carry the rail filter.
- **Result:** tested end to end — same-day second tap stays at one pass, the next day makes two, the numeral appears, and reverting to planned clears both the stamp list and the numeral. The chain bug had been live since `set-status.py` was written this afternoon; the Actions workflow that used it was therefore leaving pages stale too.
