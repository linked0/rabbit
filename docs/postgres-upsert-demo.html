Postgres Upsert Demo SHELL / SQL

온체인 이벤트 인덱서를 위한 멱등(idempotent) 적재 — INSERT ... ON CONFLICT

왜 필요한가 — 멱등성(idempotency)

블록체인 인덱서는 같은 이벤트를 두 번 이상 읽는 일이 정상입니다. (1) reorg로 블록이 갈렸다 재구성되면 같은 로그를 다시 받고, (2) 크래시 후 마지막 처리 블록부터 재시작하면 겹치는 구간을 다시 훑고, (3) RPC/큐가 보통 at-least-once(중복 가능) 전달이기 때문입니다. 그래서 "같은 입력을 몇 번 넣어도 결과가 같다"는 멱등성을 DB 레벨에서 보장해야 합니다. ON CONFLICT ... DO UPDATE(UPSERT)가 바로 그 장치입니다.

EN: A blockchain indexer normally reads the same event more than once — reorgs replay logs, restarts re-scan overlapping ranges, and RPC/queues are usually at-least-once (duplicates possible). So idempotency must be guaranteed at the DB level, and ON CONFLICT ... DO UPDATE (UPSERT) is that mechanism.

스키마 + UPSERT

CREATE TABLE bets (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tx_hash   text NOT NULL,
  log_index int  NOT NULL,
  market_id int,
  amount    numeric,
  side      text,
  UNIQUE (tx_hash, log_index)        -- ★ 충돌 타깃 = 멱등성의 닻 (먼저 있어야 함)
);

-- 있으면 갱신, 없으면 삽입 (한 문장·원자적)
INSERT INTO bets (tx_hash, log_index, market_id, amount, side)
VALUES ('0xAA', 0, 7, 100, 'YES')
ON CONFLICT (tx_hash, log_index) DO UPDATE
  SET amount = EXCLUDED.amount, side = EXCLUDED.side;

어떻게 동작하나

ON CONFLICT (tx_hash, log_index)의 괄호는 충돌 타깃입니다. INSERT를 시도하다 그 컬럼 조합이 이미 있으면 → INSERT를 버리고 DO UPDATE로 전환합니다. 이때 들어오려던 새 값은 EXCLUDED 가상 테이블로 접근합니다(EXCLUDED.amount = 방금 넣으려던 amount). 가장 흔한 실수: 충돌 타깃에 대응하는 UNIQUE 제약(또는 유니크 인덱스)이 미리 없으면 ON CONFLICT가 매칭할 대상이 없어 에러가 납니다.

EN: The parentheses in ON CONFLICT (...) are the conflict target. On a key collision, INSERT is dropped and it switches to DO UPDATE, where the incoming row is reachable via the EXCLUDED pseudo-table. Most common mistake: without a matching UNIQUE constraint/index, ON CONFLICT has nothing to match and errors out.

Docker로 한 번에 실행

# 1) 일회용 Postgres 컨테이너 띄우기
docker run --rm -e POSTGRES_PASSWORD=pw -p 5432:5432 -d --name pgtest postgres:16
sleep 5
# 2) 스크립트 실행 (psql 설치 불필요 — 컨테이너 안 psql 사용)
docker exec -i pgtest psql -U postgres < examples/pg-upsert-demo.sql
# 3) 정리
docker rm -f pgtest

행 확인 (검증 SELECT)

docker exec -i pgtest psql -U postgres <<'SQL'
SELECT id, tx_hash, log_index, amount, side FROM bets ORDER BY id;
SELECT count(*) AS total_rows FROM bets;
SQL

결과

같은 로그 (0xAA, 0)를 100 → 250으로 두 번 처리해도 1행만 남고 amount가 250으로 갱신됩니다. 다른 로그 (0xAA, 1)은 충돌이 없어 새 행(50)으로 들어갑니다.

tx_hashlog_indexamountside비고
0xAA0250YES충돌 → 100에서 250으로 갱신 (1행)
0xAA150NO충돌 없음 → 새 행

총 행 수: 2 ✅ 멱등(중복 0). 대조군으로 UNIQUE/ON CONFLICT 없이 그냥 INSERT 두 번 하면 2행 중복 ❌ (전형적인 인덱서 버그).

EN: Processing the same log (0xAA,0) twice (100 → 250) leaves a single row updated to 250, while a different log (0xAA,1) inserts as a new row (50) — two rows total, no duplicates. Without UNIQUE/ON CONFLICT, two plain INSERTs would duplicate (0xAA,0) into two rows.

DO UPDATE vs DO NOTHING

DO UPDATE SET ... 는 같은 로그를 다시 보면 덮어쓰기(데이터가 보강/정정될 때). DO NOTHING 은 이미 있으면 그냥 무시 — 로그는 불변이라 보통 이쪽이 더 흔하고 싸다. 단, reorg로 제거된 로그까지 정리하려면 block_number·removed 플래그로 별도 처리가 필요합니다.
